bigcurl Under Loss

Parallel chunked downloading is worth almost nothing on a clean link and roughly fifteenfold on a lossy one. Here is where the line falls, measured against curl, aria2c and axel across a controlled network and three real ones — and what it took to make one small tool win there.

Summary

What the numbers say

Four findings, in the order they matter.

Packet loss is the variable, not latency. A single TCP stream gets roughly MSS / (RTT · √p), so loss hurts it quadratically while N streams each get their own share. At 0.5 % loss and 100 ms RTT curl manages 1.10 MB/s; bigcurl manages 9.04, aria2c 4.88. At 250 ms and the same loss it is 0.23 against 3.42. On the same paths with no loss they are level. Curl's figure in the 100 ms cell is not a stable number — see the caveat under the sweep table.

A per-connection rate cap is the other clean win. Against nginx with limit_rate 4m, curl gets exactly 4.00 MB/s

A per-connection rate cap is the other clean win. Against nginx with limit_rate 4m, curl gets exactly 4.00 MB/s and everything parallel gets as much as the client can take: bigcurl 44.88 MB/s in adaptive mode from a one-core box, aria2c 52.67. Add a cap of eight connections per IP and both settle at the cap's 32 (31.55 and 32.20).

Real Starlink behaves like the lossy lab, not the clean one. Single-stream curl to an origin 50 ms away got 1.23 MB/s on the night of this run; bigcurl got 4.00 and aria2c 3.15. The same suite on an earlier pass measured curl at 3.60 on the same path — Starlink's baseline moves by a factor of two or three between nights, which is exactly the kind of link that rewards not depending on one stream.

On a machine with no CPU to spare, bigcurl is the slowest tool tested. A one-core VPS whose network is userspace WireGuard gives curl 73.38 MB/s and bigcurl 48.38. That is the price of running a scheduler and a process per connection on a box already at 90 %, and it is measured below rather than glossed.

Second pass · what changed

Why many small requests beat few big ones

The first report left bigcurl at half of aria2's throughput under loss and at 0.56× curl on a fast link. Tracing both to root cause took one experiment each.

Under loss, granularity is everything. At 100 ms and 0.5 % loss, aria2c with its default 1 MB pieces managed 5.72 MB/s; the same aria2c told to use 4 MB pieces managed 2.81 — identical to eight raw curls doing one 4 MB range each. And thirty-two independent curls fetching 1 MB each scored 6.61, the fastest configuration measured. Per-connection throughput under random loss varies wildly, so small work units let the lucky connections do more; a big static span hands the whole tail to the unlucky one. bigcurl now opens 32 connections (scaled down with CPU count) and sizes requests from the measured per-connection rate, so they are small under loss and large on a clean link.

On a fast link, the parent process was the ceiling. close() on a perl pipe blocks in waitpid for the child — 37 ms per curl exit on a contended box during which nobody's pipe was read. A hand-made pipe with a non-blocking reap, a 1 MB pipe buffer, and request sizing that no longer spends the first two seconds on tiny opening spans took loopback from 1231 to 1487 MB/s, past curl's 1394.

And 200 small files were costing 808 processes. One HEAD probe per file, then a span cap meant for one big file splitting each 1 MB file into four requests. Probes are now batched 25 to a curl over one connection, and no request is ever smaller than 1 MB.

What the first pass got wrong about connection reuse

The first report blamed bigcurl's loss-cell deficit on connection reuse: aria2c keeps persistent connections and bigcurl spawns a fresh curl per range, paying a handshake and a cold congestion window each time. It named curl --next — several ranges over one connection in a single process — as the biggest fix left. That was tested and it is not so: eight curls each fetching four 1 MB ranges over one kept-alive connection scored 3.02 MB/s at 100 ms and 0.5 % loss, against 3.10 for eight separate single-range curls. Reuse bought nothing. What bought 2× was request granularity handed out dynamically, which is the change that shipped. --next still has a use — a static chain of small pieces on a clean high-RTT link where handshakes dominate — but it is not the lever it looked like.

Experiment 4 · behaviour

Does it do the right thing

Speed is only half of it. Against an origin configured to misbehave, on both hosts:

  • pass server with no Range support → falls back to a single stream, bytes intact
  • pass server capping connections per IP at 4, asked for 24 → backs off, completes, bytes intact
  • pass missing file → exit 4, no output file left behind
  • pass ten consecutive kill -9 mid-transfer → resumes each time, final sha256 correct
  • pass 401 without credentials → exit 4; with -u → completes

The one place it is still beaten fairly: 200 files of 1 MB each take xargs -P8 curl 0.20 s and bigcurl 0.36 s (down from 0.75 during this pass). Probes are batched and requests are never split below 1 MB now; what remains is one curl process per file plus bookkeeping the shell loop does not do. For a directory of small files, use the shell loop.

Experiment 5 · ASK 4, does HTTP/2 multiplexing pay

One connection, many streams: not worth building

ASK 4 proposed HTTP/2 multiplexing — one connection, many streams, chosen by the tuner on clean high-RTT links only — on the theory that a shared congestion window would make it worse under loss. That was unmeasured before this pass. Verdict: do not build ASK 4. There is no regime measured here where H2 wins by a margin worth a day of implementation — tied or slower on every clean-link point large enough to reach steady state, and increasingly worse under loss up to outright failure to finish. Full method, the --max-time-per---next bug this measurement caught and fixed, and the complete verdict are in REPRODUCE.md.

Experiment 6 · ASK 2, is perl worth taking out of the byte path

Perl costs real CPU, but not the 45-vs-71 gap the roadmap assumed

ASK 2 proposed removing perl from bigcurl's byte path, citing a droplet ceiling of curl 77 / dd 71 / perl 45 MB/s. That 45 was measured against whatever pool size the tuner happened to pick, and on this CPU-bound one-core droplet the tuner overshoots badly — pinning connection count, not the tuner's choice, is what this section measures perl's cost against.

The old 45 MB/s number was the tuner, not perl

(measured, historical — ask1-parallel merge commit, one-core droplet, 1 GB, 3 reps median MB/s; not reproduced from a CSV committed to this pass, see REPRODUCE.md for the source) Pinned ladder on the same CPU-bound droplet: curl 71.9, auto 41.9, n2 61.9, n4 62.0, n8 57.7, n16 43.1, n20 38.4 — decreasing from n4 on (n2's 61.9 sits fractionally below n4's 62.0, a 0.16% inversion that is noise, not a real optimum below n4). Outcomes

Five asks, two builds, three rejections

Three of the five items on the roadmap were closed by deciding not to build them. Those rejections are the most valuable thing the measurement produced, so they are recorded here as findings with their numbers, not left as gaps in a changelog.

Name the instrument. Two of the four links below are models, and they do not agree with each other. netem applies loss independently per connection on an otherwise idle 200 Mbit path — it is a clean model of a lossy link, and it is not Starlink, which is a shared, bandwidth-capped, weather-dependent real one. Loopback is not a network at all: it measures orchestration cost with the link removed. Where the model and the real link disagree, both numbers are given.
ASK 1 — one curl per file, many rangesrejected

curl --range is a global option, not a per-transfer one. With one --range/-o pair per piece, the last range silently applies to every transfer: 16 pieces produced 16 files, each exactly 1 MB, summing to the correct total size, and every one of them contained the same block. Correct byte counts, wrong bytes — a length check passes and the file is corrupt.

Confirmed with and without -Z, via a -K config file, and independently against macOS curl 8.7.1. The correct --next form works but is a wash at matched connection count (63.9/54.5 vs 64.5/55.4 MB/s) while costing the block bitmap and byte-exact progress reporting.

(inherited) — no CSV in this tree; figures carried from the pass that measured them.

ASK 2 — take perl out of the byte pathdo not build

The premise did not survive measurement. curl's 77 MB/s and dd's 71 MB/s reproduce; the 45 MB/s attributed to perl does not, at any matched connection count — bigcurl -n N measured 57.2–58.8 MB/s at N=1/2/4, against 65.6–74.2 for the no-perl ceiling. The cited 45 was the tuner's auto-picked pool size, not perl's cost at a sane N.

perl is not free: it costs 11.2% / 19.2% / 37.9% more CPU than curl | dd at N=1/2/4, and that cost grows with N. But it separates from noise only at N=4, and the replacement needs GNU-only oflag=seek_bytes — failing the ask's own Linux-and-macOS requirement. curl -o per piece is a wash or worse.

(measured) — recomputed from ask2-droplet.csv.

ASK 3 — hedge the taillanded, off by default

The mechanism works and helps where loss is the problem: +32% at 250 ms/0.5% loss, +23% at 100 ms/0.5%, +43% against a connection-capped origin, with complete rank separation — every hedged rep beat every unhedged one.

It costs −31% on Starlink (median 4.01 s against 3.06 s), which is the link the ask itself names as the measurement to use. A duplicate on a fresh connection routes around an isolated straggler under netem's per-connection loss model; on a real shared pipe it just competes with the original for the same capacity. Ships as $HEDGE_TAIL_BLOCKS = 0; --hedge N enables it. Turning it on by default needs a runtime signal to tell the two regimes apart — see below.

(inherited) — figures recorded in cli/bigcurl's own header, not as a CSV in this tree. The default was re-read from the shipped build (measured).

ASK 4 — one connection, many H2 streamsrejected

At steady state on a clean 1 GB transfer, H2 ties H1 at 100 ms RTT (22.43 vs 22.27 MB/s) and is 1.76× slower at 250 ms (21.70 vs 12.34). Under loss it is 3.1–5.4× worse, and at 250 ms/0.5% all three H2 runs hit the 90 s cap and are recorded 0/3 verified — a failure, not a slow success.

The honest other half: on the shorter 32 MB grid H2 does win at 100 ms — 1.14× at no loss and 1.40× at 0.1%. That advantage does not survive to steady state, which makes it a slow-start artefact of the short transfer rather than a property of multiplexing. The data does not support "H2 always loses"; it supports "H2's win is confined to transfers short enough to be dominated by slow start".

(measured) — recomputed from h2-vs-h1-lab.csv and h2-vs-h1-steady.csv.

ASK 5 — beat the shell loop on many small fileslanded, target exceeded

The 200-file case went 0.371 s → 0.276 s → 0.11 s against a 0.20 s bar set by xargs -P8 curl. On this build and this host the shell loop measured 0.26 s for the same work, so bigcurl is now the faster of the two rather than merely close to it.

(measured) — remeasured on this build; the two intermediate figures are inherited from the passes that produced them.

Future work — a regime discriminator for the tunernot built

Parallel speedup separates a CPU- or contention-bound regime from a link-bound one cleanly. The CPU-bound droplet reads 1.25 against 3.74–5.88 in every other real cell — a 3× gap, with a threshold of 2.0 pre-registered before measuring and landing inside it. The clean cell replicates across passes to 0.12%. The synthetic shared-cap control also reads low (1.05), which is what a contention model should do and is a confirmation of the axis rather than a counterexample. This signal is not in bigcurl's -l trace today.

The other half did not resolve, and is reported rather than tuned into shape. The straggler ratio that would decide whether to hedge separated 39% on one pass and 14% on the next, and a clean, non-lossy cell read 1.54 on the second pass — across the 1.5 line pre-registered for it, i.e. classified as "hedge" when it should not have been. That threshold was left where it was registered and the result called ambiguous, rather than moved to make the table separate.

Findings

Thirteen defects the benchmarks found

Every one of these was invisible to the test suite and to casual use. They only appeared under measurement — and half of them were introduced by fixes to the other half, which is the argument for measuring again after every change.

Method

How to reproduce this

The harness and every raw CSV behind these figures live in onesies/bench/bigcurl/. Provision an origin, stand up the controlled network, sweep it:

ssh root@origin bash setup-server.sh      # nginx on 5 ports + fixtures + tools
lab.sh up                                 # veth pair into a netns
lab.sh set 100 0.5 200mbit                # RTT ms, loss %/direction, rate
grid.sh                                   # sweep RTT x loss, write CSV
analyze.py                                # median tables, speedup vs curl

Four rules keep the numbers honest, and each of them cost something to learn:

  • 1 verify every run — sha256 against a reference, so a fast wrong answer scores zero
  • 2 delete the output between runs, or bigcurl correctly skips a complete file and posts an absurd time
  • 3 interleave repetitions across tools; batching charges one tool for whatever the link was doing that minute
  • 4 never run two suites against one box — one overlap produced numbers 2.3× off, and they looked perfectly plausible

The five origin ports model baseline, per-connection rate cap, per-IP connection cap, no Range support, and both caps together. Both cloud hosts block inbound ports at the provider, so client traffic runs over the tailnet; both paths were confirmed direct, and the tailnet RTT matched the public RTT to within 0.2 ms.

Environment — clients: macOS 26.2 (curl 8.7.1, aria2 1.37.0, perl 5.34) and Ubuntu 24.04 (curl 8.5.0, aria2 1.37.0, axel 2.17.13). Origins: nginx 1.24.0 on Ubuntu 24.04, CUBIC, fq_codel, tcp_rmem max 6 MB. Hetzner Hillsboro OR, 16 core / 30 GB. DigitalOcean Santa Clara, 1 core / 1 GB. All figures are medians; warm-up runs discarded.
